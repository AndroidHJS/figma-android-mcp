# 三项布局改进实施方案

> 对应 [提升布局还原度的方案.md](./提升布局还原度的方案.md) 中提出的问题，本文档聚焦三个具体改动及风险分析。

---

## 改动 1：放宽布局推断公差

### 问题

`ALIGN_TOLERANCE=2dp` 太紧。子节点 x 或 y 坐标差超过 2dp 即被判定为"不对齐"，父布局保持 `mode: "none"`（绝对定位），错失 Column/Row 推断机会。

### 改动

**文件**: `src/transformers/layout.ts`

| 行号 | 常量 | 当前值 | 改为 |
|------|------|--------|------|
| 311 | `ALIGN_TOLERANCE` | `2` | `4` |
| 314 | `GAP_TOLERANCE` | `1` | `3` |

行 391（`tryInferColumn`）和行 417（`tryInferRow`）已引用 `ALIGN_TOLERANCE` 常量。行 458（`computeConsistentGap`）已引用 `GAP_TOLERANCE` 常量。无需额外代码改动。

### 风险分析

**假阳性 — 不应对齐的元素被误判为 Column/Row**

`tryInferColumn` 判断条件是 `max(xValues) - min(xValues) > ALIGN_TOLERANCE`，即子节点 x 坐标差值的**绝对范围**不超过 4dp。

考虑最坏场景：

```
子节点 x 坐标: 16, 18, 20
spread = 4 ≤ 4 → 推断为 Column
```

这 3 个节点形成垂直排列。设计师是否有意将中间节点向右偏移 2dp、底部节点再偏移 2dp？这种"阶梯式"故意偏移在 Figma 中极为罕见。Figma 使用 8dp 网格对齐，手工拖动几乎不可能精确产生 2-3dp 的故意偏移。**4dp 以内的 spread 几乎可以确定是摆放不精确。**

**假阳性 — 网格布局被误判**

2×2 网格场景：子节点分布在 (x=0,y=0), (x=0,y=50), (x=100,y=0), (x=100,y=50)

- Column 检查：x spread = 100 > 4 → **失败**
- Row 检查：y spread = 50 > 4 → **也失败**

两者都失败。**网格布局不会被误判。**

**Column 优先于 Row 的设计**

`tryInferColumn` 先于 `tryInferRow` 执行（行 361-362 `if (tryInferColumn(...)) return; tryInferRow(...);`）。如果子节点同时满足 Column 和 Row 的对齐约束（x spread ≤ 4 且 y spread ≤ 4），Column 会被优先选中。这是有意的设计选择——在移动端 UI 中垂直排列（列表、表单）比水平排列更常见。

**GAP_TOLERANCE 放宽到 3dp**

`computeConsistentGap`（行 441-461）计算相邻子节点间距，spread ≤ 3dp 时输出四舍五入后的平均值。

场景：gaps = [8, 11]，spread = 3 → 输出 gap="10dp"。实际 gap 偏差 ±1~2dp。在 160dpi 屏幕上 2dp ≈ 0.3mm，肉眼无法察觉。LLM 最终生成的代码可以根据实际需求调整精确值。

**现有测试影响**

- `layout-inference.test.ts:139-169` "x-offsets differ too much"：x 差值 20dp > 4 → 仍不推断
- `layout-inference.test.ts:294-321` "y-offsets differ too much"：y 差值 20dp > 4 → 仍不推断
- `layout-inference.test.ts:103-137` "does NOT set gap when spacing is inconsistent"：gaps [20, 8] spread=12 > 3 → 仍不输出 gap

**结论：现有测试全部通过，无新增假阳性风险。**

## 改动 2：移除 convertFixedChildrenToFillMax 对 INSTANCE 的跳过

### 问题

`convertFixedChildrenToFillMax` 跳过所有 `id.startsWith("I")` 的子节点（INSTANCE 内部节点）。导致组件实例内居中固定宽度/高度的子节点保持 `fixed` 而非转为 `fill + padding`，丧失了响应式布局能力。

### 改动

**文件**: `src/transformers/layout.ts`

- 删除第 536 行 `if (child.id.startsWith("I")) continue;`
- 更新第 502-508 行 JSDoc 注释，移除 "Does not recurse into INSTANCE internal children (ids starting with "I")."

**文件**: `src/tests/layout-fillmax.test.ts`

- 第 140-163 行测试 "skips instance internal child" → 将断言从 `expect(unchanged.sizing?.horizontal).toBe("fixed")` 改为 `expect(updated.sizing?.horizontal).toBe("fill")`

### 风险分析

**原始 guard 的行为**

代码有两层逻辑：

1. 行 536：`tryConvertChildren` 里跳过 INSTANCE 子节点 → **阻止转换**
2. 行 522-524：递归 `convertFixedChildrenToFillMax(node.children)` → **不阻止递归**

JSDoc 说"Does not recurse into INSTANCE internal children"，但实际上递归会深入 INSTANCE 子树，只是在当前层级不转换 INSTANCE 的直接子节点。JSDoc 描述和代码行为不完全一致。

**移除是否会破坏组件样式共享？**

`tryConvertHorizontal`（行 571-588）和 `tryConvertVertical`（行 611-628）的修改流程：

```
1. const clone: SimplifiedLayout = { ...childLayout }   // 浅拷贝
2. 修改 clone 的 sizing / dimensions / padding
3. globalVars.styles[newKey] = clone                     // 新 key
4. child.layout = newKey                                 // 节点指向新 key
```

关键：**原 layout 对象完全未被修改**。如果同一个 layout key 被多个 INSTANCE 子节点共享（例如同一组件的多个实例），行 571 的浅拷贝确保每个节点得到独立的 clone，修改不会互相影响。**不影响组件共享样式。**

**INSTANCE 子节点本身是 auto-layout 容器的情况**

行 540 有另一个 guard：`if (childLayout.mode === "row" || childLayout.mode === "column") continue;`。如果 INSTANCE 子节点本身是 auto-layout 容器，会被这个 guard 跳过（不转换容器自身，其子节点由递归处理）。移除 INSTANCE guard 后行为不受影响。

**结论：安全。clone + newKey 机制已保证隔离。**

## 改动 3：新增 regionHints 结构化输出

### 问题

`inferAutoLayoutFromPositions` 只做**全集推断**：父节点的所有 eligible children 必须形成单一 Column 或 Row。多区域页面（顶部 header + 中间内容 + 底部导航）的全集推断失败，父布局保持 `mode: "none"`，LLM 拿到裸坐标需要自己推测分组。

`layoutHints` 只给屏幕级通用规则（fillMax、weight、elevation 替代等），与节点树内容无关，每次返回相同的文本数组。

### 设计决策

| 问题 | 选择 |
|------|------|
| 输出格式 | 独立结构化字段 `regionHints`（非嵌入 layoutHints 文本数组） |
| 数据类型 | 类型化数组 `RegionHint[]`，每个 hint 包含 parentId/name + regions[] |
| 分桶策略 | 锚点分组法（避免简单 round 分桶的边界断裂） |
| 列/行推断 | Column 优先于 Row（与现有推断一致） |
| 输出阈值 | regions ≥ 2 才输出（单 region = 无需分组提示） |

### 新增类型

```typescript
// src/transformers/region-hints.ts

interface RegionGroup {
  /** 省略表示 singleton（单子节点区域，不需要容器建议） */
  mode?: "column" | "row";
  childIds: string[];
  childNames: string[];
  /** 多子节点区域的统一间距，不一致时为 undefined */
  gap?: string;
}

interface RegionHint {
  parentId: string;
  parentName: string;
  regions: RegionGroup[];
}
```

### 输出示例

```yaml
regionHints:
  - parentId: "1:2"
    parentName: "Dashboard"
    regions:
      - mode: column
        childIds: ["1:3", "1:4"]
        childNames: [Header, SearchBar]
        gap: "8dp"
      - mode: row
        childIds: ["1:5", "1:6"]
        childNames: [LeftPanel, RightPanel]
        gap: "12dp"
      - childIds: ["1:7"]
        childNames: [Footer]
```

### 算法

```
generateRegionHints(nodes, globalVars) → RegionHint[]:

  遍历节点树（递归，与 inferAutoLayoutFromPositions 相同遍历模式）:

    processParent(parent):
      A. 跳过已推断的 auto-layout 父节点（mode !== "none"）
      B. 收集 eligible children：
         - 必须有 layout key
         - 必须有 locationRelativeToParent
         - 不能是 position: "absolute"
         - < 2 个 → 跳过
      C. 锚点分组法按 x 聚类 → 同组内按 y 排序检查无重叠 → Column region
         已分配的子节点加入 assigned set
      D. 对未分配子节点按 y 聚类 → 按 x 排序检查无重叠 → Row region
      E. 剩余未分配子节点 → singleton region
      F. regions.length >= 2 → 输出 RegionHint

锚点分组法:
  将子节点按目标 axis 排序
  遍历: 与每个已有 group 的 anchor（第一个元素的值）比较
        差距 ≤ ALIGN_TOLERANCE → 加入该 group
        否则 → 新建 group
```

### 分桶策略：锚点分组法 vs 简单 Round

**`Math.round(x)` 分桶的问题**：

x=16.4 和 x=17.1 相差 0.7dp（远小于 ALIGN_TOLERANCE=4），但分别 round 到 16 和 17 → **不同桶**。Figma 坐标极少出现这种小数组合，但不够健壮。

**锚点分组法**（采纳）：

```typescript
function groupByAlignment(
  data: ChildDatum[],
  axis: "x" | "y"
): ChildDatum[][] {
  const sorted = [...data].sort((a, b) => a[axis] - b[axis]);
  const groups: ChildDatum[][] = [];
  for (const item of sorted) {
    const group = groups.find(
      (g) => Math.abs(g[0][axis] - item[axis]) <= ALIGN_TOLERANCE
    );
    if (group) {
      group.push(item);
    } else {
      groups.push([item]);
    }
  }
  return groups;
}
```

排序后，每个元素只比对每个 group 的**第一个元素**（anchor），而非与相邻元素比较。不会出现传递链问题（[0, 3, 6, 9] 不会因为相邻差 ≤4 而全部合入一组，因为 6 与 anchor=0 差 6 > 4）。

### 风险分析

**风险 1：Singleton 噪音**

5 个子节点中 2 个形成 Column、3 个各在不同位置 → 输出 4 regions（1 Column + 3 singletons）。LLM 需要能忽略无关 singleton。

**缓解**：
- multi-child regions 排在前面，singletons 排在后面
- singleton 不含 mode/gap 字段，结构明显不同
- 后续可增加 "singleton 合并" 逻辑（空间相邻的多个 singleton 合并为一个 region）

**风险 2：与 inference 结果的交互**

`inferAutoLayoutFromPositions` 在 pipeline 中先于 regionHints 运行。被推断为 Column/Row 的父节点 `mode` 已变，regionHints 的 Step A 会跳过它们。只有推断失败（mode 仍为 "none"）的节点才进入 regionHints 分析。

场景验证：父节点 A 有 3 个子节点，x=[16, 17, 200]
- Column 推断：spread = 184 > 4 → **失败**（因为有一个 x=200 的元素）
- 进入 regionHints：x≈16 的 2 个节点分入 Column region，x=200 的单节点分入 singleton → 2 regions → 输出 hint ✅

**风险 3：子节点不完整**

部分子节点没有 `locationRelativeToParent`（纯 auto-layout 子节点、无布局信息节点等）被 `collectEligibleChildren` 排除。regionHints 不提及它们。这与 `inferAutoLayoutFromPositions` 行为一致。LLM 从 `nodes` 树中可以看到完整 children 列表。

**风险 4：无 layout 的父节点**

Step A 的 `!parent.layout` 检查会使无 layout 的节点直接跳过。如纯矢量图被 collapse 后的 IMAGE-PNG 节点。图片节点不需要布局建议。

**风险 5：空 regionHints 数组**

与 `layoutHints` 一致：无有意义分组时输出 `regionHints: []`。LLM 知道此字段始终存在，空数组表示 "无需额外分组，使用现有 mode 字段即可"。

### 已知局限（不在此次改动范围）

1. **不检测重叠**：[提升布局还原度的方案.md](./提升布局还原度的方案.md) 方案中的重叠检测（连通分量 + union-find + 15% 面积阈值）在此次不实现。重叠子节点会在 Step C/D 中因 `hasOverlap` 检查失败而散落到 singleton。后续可单独增强。
2. **不输出 Z-order**：regionHints 不描述同 region 内子节点的堆叠顺序。children 数组顺序本身即为 Figma 渲染顺序（索引 0 = 最底层），LLM 可直接使用。
3. **不跨层级建议**：只描述单个父节点下的分组，不输出跨层级的嵌套结构建议（如 "外层 LinearLayout vertical 包裹 FrameLayout + LinearLayout"）。

### Pipeline 集成

```
当前 pipeline:
  fetch → simplify
  → inferAutoLayoutFromPositions   (行 170)
  → convertFixedChildrenToFillMax  (行 174)
  → writeLogs                      (行 176)
  → mapLayoutStyles                (行 192)
  → generateLayoutHints            (行 194)
  → serialize                      (行 196)

修改后:
  fetch → simplify
  → inferAutoLayoutFromPositions   (行 170)
  → convertFixedChildrenToFillMax  (行 174)
  → generateRegionHints            (行 175 NEW)
  → writeLogs                      (行 176)
  → mapLayoutStyles                (行 192)
  → generateLayoutHints            (行 194)

```

`generateRegionHints` 放在 `mapLayoutStyles` **之前**，因为它需要读取 `SimplifiedLayout.mode`（"none"/"row"/"column"），这些是平台无关的值。`mapLayoutStyles` 会将 layout 转换为 ComposeLayout 或 ViewsLayout，改变 mode 字段结构。
