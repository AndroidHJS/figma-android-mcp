# MCP 布局策略增强方案

## 背景

`figma-android-mcp` 当前有两套机制处理布局：

1. **`layoutHints`**（`src/services/get-figma-data.ts:27-62`）— 纯通用规则：`match_parent` 规则、FrameLayout 根容器、elevation 替代等。**与节点树内容无关**，每次返回相同内容。

2. **`inferAutoLayoutFromPositions`**（`src/transformers/layout.ts:340-437`）— 分析了子节点位置关系，但输出是**隐式**的（直接改 styles 数据字段），且**只检测** Column/Row 流式排列，不检测重叠（overlap）。

## 核心问题

当 `inferAutoLayoutFromPositions` 无法将节点识别为 Column/Row 时（例如兄弟节点有重叠），父布局保持 `mode: "none"`。AI 拿到的是一组裸坐标（`locationRelativeToParent`），需要自己做空间推理——而 LLM 不擅长这个。结果就是：

- 重叠场景用 LinearLayout 硬排 → 乱调 margin
- 不自觉选 ConstraintLayout → XML 膨胀 3 倍
- Z-order 丢失 → 背景盖在前景上
- 混合场景（部分重叠 + 部分流式）→ 完全不会拆

## 总体目标

在 `get_figma_data` 的输出中新增 **per-parent 显式布局策略文本**，让 AI 不需要自己做空间推理。

输出示例：

> ```
> NODE layout_PBUF1T (父容器，344dp×258dp): 3 children
>   → 重叠组[obj_2, obj_3] 用 FrameLayout 叠放，child[0] 在下 child[1] 在上
>   → 流式组[obj_1, obj_4] 用 LinearLayout vertical，gap=12dp
>   → 建议结构：FrameLayout(重叠组, height=wrap_content) + LinearLayout(流式组, height=0dp, weight=1)
> ```

## 改动清单

### 改动 1：重叠检测 + 连通分量分组

**文件**：`src/transformers/layout.ts`（新增若干函数）

**输入**：同一父节点下的一组 ChildLayoutData（含 x, y, width, height）

**输出**：分组列表——每个分组标记为 `"overlap"`（需 FrameLayout）或 `"flow"`（需 LinearLayout）

**算法**：

```
1. 对每个子节点对 (i, j)，计算 bounding box 重叠面积
2. 重叠面积 > 两者最小面积的 15% → 标记为重叠边
3. 在重叠边构成的图上运行连通分量算法（union-find）
4. 每个包含 ≥2 个节点的连通分量 → overlap 组，建议 FrameLayout
5. 连通分量外的孤立节点 → flow 候选，进入 Column/Row 检测（复用现有 tryInferColumn/tryInferRow，但放宽 X/Y 公差到 8dp）
6. 同一父节点下可能同时存在 overlap 组和 flow 组 → "混合模式"
```

**伪代码**：

```ts
interface SiblingGroup {
  type: "overlap" | "flow";
  direction?: "column" | "row";   // only for flow groups
  gap?: string;                    // only for flow groups
  children: number[];              // indices into parent.children
}

function analyzeSiblingLayout(data: ChildLayoutData[]): SiblingGroup[] {
  // Step 1: build overlap graph
  const overlapEdges: [number, number][] = [];
  for (let i = 0; i < data.length; i++) {
    for (let j = i + 1; j < data.length; j++) {
      if (computeOverlapRatio(data[i], data[j]) > 0.15) {
        overlapEdges.push([i, j]);
      }
    }
  }
  
  // Step 2: connected components (union-find)
  const components = findConnectedComponents(data.length, overlapEdges);
  
  // Step 3: classify each component
  const groups: SiblingGroup[] = [];
  for (const comp of components) {
    if (comp.length >= 2) {
      groups.push({ type: "overlap", children: comp });
    } else {
      // Try flow detection on isolation nodes that are near each other
      // (relaxed tolerance, 8dp)
      // ...
    }
  }
  
  return groups;
}
```

### 改动 2：生成显式布局策略文本

**文件**：`src/services/get-figma-data.ts`

**函数**：`generateLayoutHints` → 扩展为 `generateEnhancedLayoutHints`

当前签名只接收 `screen`：

```ts
function generateLayoutHints(screen: { width: string; height: string }, platform: Platform): string[]
```

**修改后**追加 `nodes` 和 `globalVars`：

```ts
function generateEnhancedLayoutHints(
  screen: { width: string; height: string },
  nodes: SimplifiedNode[],
  globalVars: GlobalVars,
  platform: Platform,
): string[] {
  const hints = generateLayoutHints(screen, platform); // 保留通用规则
  
  // 新增：per-parent 策略
  const strategyHints = generatePerParentStrategies(nodes, globalVars);
  return [...hints, ...strategyHints];
}
```

**`generatePerParentStrategies`** 遍历节点树，对每个有 ≥2 个 eligible children 的父节点：

1. 收集 children 的 layout 数据（复用 `collectEligibleChildren`）
2. 调用 `analyzeSiblingLayout` 得到分组
3. 按模板生成文本

**模板示例（Views 平台）**：

| 场景 | 输出 |
|------|------|
| 纯重叠（单组，所有 children 都重叠） | `NODE layout_XXX（W×H）: 3个children全部重叠 → 使用 FrameLayout。child[0] 在最底层，child[2] 在最上层。` |
| 纯流式 Column | `NODE layout_XXX（W×H）: 5个children X轴对齐（最大偏差2dp），Y轴顺序排列无重叠 → 使用 LinearLayout vertical，gap=12dp。` |
| 混合模式 | `NODE layout_XXX（W×H）: 分为2组 — 重叠组[child1,child2] 建议 FrameLayout；流式组[child3,child4,child5] 建议 LinearLayout vertical(gap=12dp)。建议结构：FrameLayout(height=wrap_content) + LinearLayout(height=0dp,weight=1) 放在外层 LinearLayout vertical 中。` |

**调用位置**：`getFigmaData()` 中 `mapLayoutStyles` 之后、`serializeResult` 之前（约 192-196 行）。

### 改动 3：补 Z-order 字段

**文件**：`src/transformers/layout.ts` 的 `buildSimplifiedLayout` 或 `buildSimplifiedFrameValues`

当前简化后的布局数据没有显式 Z-order。重叠检测需要知道谁在上谁在下。

**方案**：给 `SimplifiedLayout` 加一个可选字段 `zIndex?: number`，在 `frameValues` 中设为 children 数组索引（0 = 最底层）。

```ts
// 在 buildSimplifiedFrameValues 中
frameValues.zIndex = (parent?.children ?? []).indexOf(n);
```

→ 但更简单的方式是：children 数组顺序本身就是 Figma 的渲染 Z-order（第一个 = 最底层）。所以策略文本直接用 "child[0] 在下 child[1] 在上" 即可，不需额外字段。

### 改动 4：放宽流式检测公差

**文件**：`src/transformers/layout.ts`

当前：

```ts
const ALIGN_TOLERANCE = 2; // dp
```

改为：

```ts
const ALIGN_TOLERANCE = 8; // dp — 放宽到 8dp，小偏差靠 marginStart/marginTop 表达
```

> 注意：这个改动会影响 `inferAutoLayoutFromPositions` 的推断行为——更多父节点会被识别为 Column/Row。需要权衡：放宽后假阳性（把本不该分组的节点硬识别为 Column）风险增加。可以只在新策略文本分析中放宽，不影响原有推断逻辑。

### 改动 5：增加面积阈值

**文件**：新代码在 `src/transformers/layout.ts`

```ts
const OVERLAP_AREA_RATIO_THRESHOLD = 0.15; // 重叠面积 < 较小元素面积的 15% 时忽略
```

解决阴影、描边等造成的假重叠。

## 出错情况处理

| 场景 | 行为 |
|------|------|
| 父节点无 children | 跳过，不生成策略 |
| children 全部 absolute | 视为纯重叠组，建议 FrameLayout |
| children 的 layout 数据不完整（缺 bounding box） | 跳过该 child，不参与分组 |
| 重叠面积恰好在阈值边缘 | 阈值可调（15%），边缘案例偏向"不重叠"（防止过度 FrameLayout 化） |
| 父节点本身已是一个重叠组的 child | 跳过，不做递归策略（避免嵌套 FrameLayout 的策略文本过长） |

---

## 不改动的部分

- **不修改 `inferAutoLayoutFromPositions` 的现有行为** — 它继续隐式修改 styles。策略文本是额外的、显式的、human-readable 层。
- **不修改 `SimplifiedLayout` 接口** — 策略文本不依赖新字段，纯粹从现有数据推导。
- **不影响 `download_figma_images`** — 改动局限于 `get_figma_data` 的序列化阶段。
- **Compose 平台** — 策略文本模板同样适用，只需把 `FrameLayout`→`Box`、`LinearLayout`→`Column/Row`。

## 验证方式

1. 用 WWMB 产品列表页（`980-3716`）的 nodeId 重新调用 `get_figma_data`（`outputPlatform=views`）
2. 检查 `layoutHints` 数组中是否出现 per-parent 策略文本
3. 重点验证：
   - banner 区域（重叠组 → FrameLayout 建议）
   - 产品卡片区域（流式 Column → LinearLayout vertical 建议）
   - 底部状态卡片区域（混合模式 → 嵌套建议）
4. 用增强后的 hints 重新生成 XML，对比之前未增强的版本，确认布局策略选型是否正确

---

## 实施顺序建议

1. **先做改动 1 + 2**（重叠检测 + 策略文本生成）— 这是核心价值，其他是锦上添花
2. **再做改动 5**（面积阈值）— 防止假阳性，属于改动 1 的自然补充
3. **改动 4**（放宽公差）— 独立测试，观察假阳性率
4. **改动 3**（Z-order）— 实际不需要（children 顺序已有），可跳过
